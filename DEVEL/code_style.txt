GnollHack Coding Style
=======================

GnollHack is written in C (C99 standard), with a .NET MAUI frontend in C#.
This coding style document is concerned primarily with the style used for C
source files. For C# conventions, see the AI agent skills documentation.

GnollHack is derived from NetHack 3.6.2. The original NetHack codebase used
K&R brace placement style and K&R function declarations. GnollHack has fully
migrated to Allman brace placement style and ANSI C function prototypes.
Always use the GnollHack style described here.

Developers should do their best to adhere to the coding style to promote
legible, easy-to-edit code. Legibility is paramount, so in some cases, it may
be better not to fully adhere to the style guidelines.

Recipes for common text editors can be found at the end of this file.

Indentation and Spacing
-----------------------

The basic indentation is 4 spaces wide. All indentation is done using space
characters, not tabs.

Lines should be at most 78 characters wide. If a line would be longer than the
limit, the line should be wrapped and the wrapped portion should be aligned
with the parentheses or brackets containing the wrap. If there is no set of
parentheses or brackets, the line should be indented four spaces. Wrapping
should normally occur after a comma or before a binary operator, when
possible:

    int index
        = SomeExcessivelyLongExpression;

    fcall(arg1,
          arg2, (cond13
                 && cond2));

Single blank lines should be used wherever convenient to improve readability.

Non-C File Indentation Standards
---------------------------------

GnollHack contains many non-C files (MSBuild project files, XAML layouts,
JSON configs, etc.). These files follow industry-standard indentation
conventions, which are enforced by the .editorconfig at the repository root.

  File type(s)                                     Indentation
  -----------------------------------------------  -----------
  .csproj, .vcxproj, .proj, .props, .targets       2 spaces
  .vcxproj.filters, .projitems, .shproj            2 spaces
  .xml, .config, .manifest, .resx, .nuspec         2 spaces
  .json                                            2 spaces
  .yaml, .yml                                      2 spaces
  .xaml                                            4 spaces
  .cs (C#)                                         4 spaces
  .c, .h (C)                                       4 spaces
  .sln (VS solution)                               Tabs

These conventions match what Visual Studio, dotnet new, and the official
Microsoft .NET repositories (dotnet/runtime, dotnet/maui, dotnet/roslyn)
use by default.

When editing any of these files, ensure that the indentation matches the
table above. Do not use tabs in any file except .sln files.

Naming Conventions
------------------

GnollHack C code uses snake_case for identifiers:

- Function names: snake_case (e.g., min_npc_appearance_depth, mon_is_gecko)
- Variable names: snake_case (e.g., signed_glyph, layer_flags, npc_room)
- Struct field names: snake_case (e.g., animation_name, number_of_tiles)
- Macro names: ALL_CAPS_WITH_UNDERSCORES (e.g., NPC_FLAGS_NO_GENERATION,
  LAYER_FLOOR, MENU_FLAGS_IS_HEADING)
- Enum values: ALL_CAPS_WITH_UNDERSCORES (e.g., LAYER_FLOOR, MAX_LAYERS)

All enums and #define constants that are used across the C/C# interop boundary
follow C naming conventions (ALL_CAPS_WITH_UNDERSCORES) so that identifiers
can be found easily with a single search across both codebases.

Functions and Control Statements
--------------------------------

GnollHack uses Allman brace placement style: the opening brace appears on its
own line, at the same indentation level as the control statement or function
definition header.

For a function definition, the return type, declarator, and opening brace
should each appear on a line of their own, using standard ANSI C prototypes:

    static boolean
    has_npc_room(struct monst *npc)
    {
        /* function body */
    }

Opening braces of control statements appear on their own line (Allman style):

    if (condition)
    {
        /* body */
    }

Else statements and the while statements of do-while blocks appear on the
next line after the closing brace:

    if (condition)
    {
        /* body */
    }
    else if (condition)
    {
        do
        {
            /* body */
        } while (condition);
    }
    else
    {
        /* body */
    }

If a control block has only a single statement, it can appear on a line of its
own, with an indent, either with or without braces. Use whichever is clearer
and sufficiently risk-free in the context. However, avoid using the comma
operator to combine multiple assignments into a single-statement body:

    /* Both of these are acceptable: */
    if (condition)
        fcall();

    if (condition)
    {
        fcall();
    }

    /* BAD: do not combine assignments with comma in a single-statement body */
    if (condition)
        x = 1, y = 2;

If a null statement is needed, it should be expressed as an empty set of
braces, not with a semicolon, because many compilers will warn if a null
statement is used:

    if (condition)
    {
    }
    else
        fcall();

Switch statements should have the case labels unindented, and the statements
should be indented normally. The default case should occur last unless there's
a compelling reason not to, and fallthroughs should be explicitly marked as
such with a comment, to avoid Yeenaghu getting the touch of death again:

    switch (condition)
    {
    case FOO:
    case BAR:
        fcall();
        /* fall-through */
    case BAZ:
        fcall();
        break;

    default:
        statement;
    }

Variables may be declared close to where they are first used, not only at the
top of a block. This improves readability by keeping declarations near their
first use:

    /* Both of these are acceptable: */
    int count = 0;
    for (i = 0; i < n; i++)
    {
        /* ... */
        int result = some_function(i);
        count += result;
    }

Variables should never be declared in a condition. For for-loop
initialization, prefer C89-style declarations (variable declared before the
loop) because some compilers may generate warnings for loop-scoped
declarations. Loop-scoped declarations are not banned but should be avoided
when practical:

    /* Preferred: */
    int i;
    for (i = 1; i < 10; ++i)
    {
        /* body */
    }

    /* Acceptable but may warn on some compilers: */
    for (int i = 1; i < 10; ++i)
    {
        /* body */
    }

If an assignment is used as a condition, it should be
wrapped in an additional set of parentheses for clarity:

    int *p;
    if ((p = fcall()))
    {
        /* body */
    }

Spaces in Expressions
---------------------

Spaces should appear around binary operators, after commas, after a C-style
cast, and after the keyword in a control statement. They should not appear
between a function name and the opening parenthesis of a function call, nor
immediately inside a pair of parentheses:

    foo(i, j, l);
    if ((boolean) condition)
    {
        /* body */
    }

Comments
--------

Use /* */ for all regular C comments. The // comment style may be used to
comment out code or to quickly retain old code at the end of a line, but
/* */ is the generally preferred comment style for documentation and
explanatory comments:

    /* This is the preferred comment style for explanations. */
    result = calculate_damage(mtmp);

    //old_result = legacy_damage(mtmp);  /* OK: commented-out code */
    x = 5; //was 3  /* OK: quick inline note about old value */

C99 Features
------------

GnollHack targets the C99 standard. The following C99 features are used or
permitted:

- long long int (and unsigned long long int): Used throughout for 64-bit
  values, formatting with %lld/%llu, and the int64_t/uint64_t typedefs.
- Mixed declarations and code: Variables may be declared close to first use
  (see the Variables section above).
- // comments: Permitted for commenting out code (see Comments above).
- <stdint.h> fixed-width types: int32_t, uint64_t, etc. are used where
  appropriate, especially for interop with the C# frontend.
- snprintf: Preferred over sprintf when a buffer size limit is needed.

The following C99 features are NOT used or are explicitly banned:

- Variable-length arrays (VLAs): BANNED. MSVC does not support them, and
  they carry stack overflow risk. Always use fixed-size arrays or dynamic
  allocation.
- Designated initializers (e.g., .field = value): Avoid. Not currently used
  in the codebase.
- Compound literals: Avoid. Not currently used in the codebase.
- Variadic macros (__VA_ARGS__): No strong need. Avoid unless clearly
  beneficial.
- restrict qualifier: Not used.
- _Pragma operator: Not used.
- Flexible array members: Not used (the traditional struct hack suffices).
- <stdbool.h> / bool: Not used. GnollHack has its own boolean type.
- inline functions: Rarely used (only in the PRNG code). Not actively
  encouraged.

Legacy Code Notes
-----------------

GnollHack's C codebase has been fully converted from the original NetHack K&R
function declaration style to ANSI C function prototypes. The old
FDECL/NDECL/VDECL prototype macros are no longer used. Some files may still
retain older formatting or K&R brace placement in places; when touching such
code, convert it to the GnollHack Allman style described in this document.

Vim Configuration
=================

For vim, the following settings are encouraged when editing GnollHack code, to
ensure that indentation is done correctly:

    set shiftwidth=4
    set softtabstop=4
    set expandtab
    set tabstop=4
    set shiftround
    set textwidth=78
    set cindent
    set filetype=c


Visual Studio Configuration
===========================

In Visual Studio under Tools->Options->Text Editor->C/C++, you can set the 
following options to obtain desired behavior:

[Tabs]
Indenting: Smart
Tab size: 4
Indent size: 4
Insert Spaces

There are a number of other options under [Formatting] that should be
checked (Indentation, New Lines, Spacing, and Wrapping), but there are so
many entries that reproducing them here is impractical. Fortunately, the 
options are in plain English, so walking through them with a copy of 
this Guide handy and making changes as required will suffice.

Emacs Configuration
===================

There are no doubt umpteen different ways to handle this in Emacs.
Putting the following in ~/.emacs.el is one

(defun hook-c ()
  (setq c-set-style "bsd")
  (setq c-basic-offset 4)
  (setq indent-tabs-mode nil))
(add-hook 'c-mode-common-hook 'hook-c)
